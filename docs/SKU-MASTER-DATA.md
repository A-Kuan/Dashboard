# SKU 主数据与编辑模块

SKU 编辑页用于统一维护零件身份、OE 对照、车型适配和 EPC 来源证据。前端路由：

- 新建：`/skus/new`
- 编辑：`/skus/:skuId/edit`

当前版本通过独立 Node.js API 访问 PostgreSQL。前端不直接访问数据库，数据库默认不写入演示 SKU。

列表、详情、搜索和编辑页必须忠实展示数据库值。缺少商品图片或 EPC 图组时显示明确空状态，缺少文本值时显示 `—`；禁止回退到演示零件图、虚构数据来源、固定操作人或固定通知数量。身份系统接入前，新产生的审计记录统一标记为“系统操作员”。

## 信息模型

### 1. 基本信息

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| SKU 编码 | 是 | 内部唯一编码，保存前校验唯一性；仅允许英文字母、数字、空格和常用零件号符号 |
| 中文名称 | 是 | 面向采购、库存和销售的标准名称 |
| 品牌 | 是 | 使用 `sku_brand` 字典 |
| 零件大类 | 是 | 使用 `part_category` 字典 |
| 零件小类 | 否 | 可按大类维护级联字典 |
| 制造商零件号 | 否 | MPN / 厂商件号；填写时仅允许英文字母、数字、空格和常用零件号符号 |
| 主 OE 号 | 是 | 当前有效的首选 OE 编号；仅允许英文字母、数字、空格和常用零件号符号 |
| 计量单位 | 是 | 使用 `unit` 共享字典；新建时不预选，需由用户确认 |
| 生命周期状态 | 是 | 草稿、在售、停产等业务状态 |
| 条形码 / GTIN | 否 | EAN、UPC 或企业内部条码 |
| 商品主图 | 否 | 支持上传、更换和删除；删除后需保存 SKU 才会持久化 |

### 2. OE 与替代关系

一个 SKU 可关联多个 OE、历史号和替代号。每条关系包含：编号类型、OE/替代号、关系方向、数据来源、可信度和核验状态。编号类型、替代关系、数据来源和可信度使用共享字典；第一条关系会带入当前主 OE 和数据来源。品牌属于 SKU 主信息，不在替代关系中重复填写。替代链必须保留先后顺序，不能只覆盖旧号。

### 3. 适配车型

每条适配记录至少包含：品牌、车型/平台、年款范围、发动机、车身形式、适配条件、市场、数据来源和核验状态。车身形式、数据来源和验证状态使用共享字典；车型、年款、发动机和适配条件保留结构化文本输入，后续可接车型主数据模块。VIN、PR/选装代码、安装位置、左右侧和排除条件作为精确匹配条件扩展。

### 4. 技术规格与包装

包含材质、颜色、表面处理、尺寸、重量、包装数量、套件明细及按零件分类变化的技术属性。分类属性应由后端属性模板驱动，不在页面硬编码。

### 5. 采购、库存与销售

SKU 主数据保存默认供应商、供应商件号、采购单位、最小起订量、交期、补货点、安全库存、包装尺寸、产地和海关编码。实时库存、锁定量、在途量、业务销售价及 OEM 参考价是派生或来源数据，编辑页只读展示，不作为普通主数据覆盖。

### 6. 媒体与来源

包含商品图库、EPC 图组、安装文档、证书和视频。来源记录需保存来源系统、目录/图组、位置号、原始名称、同步时间和原始数据标识，便于审计与回溯。

### 7. 数据治理

系统自动维护创建人、创建时间、更新人、更新时间和版本，并记录每次创建、保存和发布操作。保存与发布必须携带读取时的数据版本；版本已变化时返回 409，避免多人编辑互相覆盖。发布前强制校验基本信息、与主 OE 一致的 OE 关系、至少一条适配车型和数据来源；图片与条码作为建议补充项。完整审批流和字段级差异明细属于后续阶段。

## 前端组件

- `SkuEditor`：编辑页编排、保存状态和路由模式。
- `EditorField` / `TextField` / `StaticSelect`：统一字段结构和校验表现。
- `DictionarySelect`：品牌、分类、计量单位、数据来源等共享可搜索字典选择器；编辑场景排除筛选专用的“全部”。
- `DictionaryCell`：OE 与适配表格中的紧凑字典选择器，兼容历史值并过滤已停用选项。
- `OeRelations`：OE 与替代关系表。
- `FitmentTable`：车型适配表。
- `EvidencePanel`：EPC 原始记录、字段对比、差异处理和发布检查。

SKU 列表支持品牌、零件大类、状态、数据来源和适配完整度筛选，并可按最近更新、SKU 编码、中文名称或状态排序。筛选结果变化时同步切换详情记录，避免继续展示已被过滤的 SKU。

## 后端接口

SKU API 位于 `apps/api`，提供：

- `GET /api/v1/skus?q=<keyword>`：列表或按 SKU、OE、名称、品牌、分类和车型搜索。
- `GET /api/v1/skus/:id`：读取 SKU 聚合详情。
- `POST /api/v1/skus`：创建 SKU。
- `PUT /api/v1/skus/:id`：更新主数据草稿。
- `POST /api/v1/skus/:id/publish`：完成校验并发布。
- `POST /api/v1/skus/:id/discontinue`：将带当前版本的在售 SKU 标记为停产，并写入变更记录。
- `POST /api/v1/skus/validate-code`：校验 SKU 编码唯一性。
- `GET /api/v1/dictionaries`：读取共享业务字典。
- `PUT /api/v1/dictionaries`：保存共享业务字典。
- `POST /api/v1/dictionaries/reset`：恢复默认字典。

数据库使用 `sku`、`sku_oe_relation`、`sku_fitment`、`sku_change_log` 和 `app_configuration` 表。每次更新递增 `sku.version`，OE 与适配记录使用外键级联并在同一事务中替换；`sku_change_log` 保存版本、操作、操作人、时间与关系数据摘要。

本地开发先启动 API，再启动前端；Vite 将 `/api` 代理到 `127.0.0.1:4183`。生产环境由 Nginx 将 `/sku-preview/api/` 转发到同一端口。
