# 技术选型与系统架构

- 状态：已采用
- 适用项目：Dashboard 汽配 ERP
- 决策日期：2026-09-27
- 架构原则：前后端分离、模块化单体、契约优先、审计优先

## 1. 项目目标

Dashboard 面向汽配行业的 SKU 管理、VIN/OE/EPC 查询、车型适配、库存、采购和销售业务。系统需要重点保证：

- SKU、OE 号和车型适配关系准确且可追溯；
- EPC 原始数据与人工维护数据有明确边界；
- 大数据表格、组合筛选和批量操作保持流畅；
- 导入、导出、EPC 同步等长任务不阻塞普通接口；
- 权限、价格、库存及关键字段变更可以审计；
- 前端、API 和后台任务能够独立构建、部署和扩容。

## 2. 架构结论

采用以下技术基线：

> React + TypeScript + Vite + TanStack + Radix UI/Tailwind CSS  
> NestJS + Fastify + OpenAPI  
> PostgreSQL + Drizzle ORM  
> Redis + BullMQ + S3 兼容对象存储

代码使用 Monorepo 管理，但运行时保持前后端分离：

```text
浏览器
  │
  ├── Web 前端（React/Vite，独立部署）
  │       │
  │       └── HTTPS / REST API
  │
  └── API 服务（NestJS/Fastify，独立部署）
          ├── PostgreSQL
          ├── Redis
          ├── S3 兼容对象存储
          └── Worker 后台任务
                  ├── EPC 数据同步
                  ├── SKU 批量导入
                  ├── Excel/CSV 导出
                  └── 图片与附件处理
```

前后端分离指独立应用、独立构建和独立部署，不要求拆成多个 Git 仓库。首期采用一个仓库可以统一接口类型、枚举、质量检查和版本变更。

## 3. 技术选型

### 3.1 前端

| 类别 | 选型 | 主要职责 |
| --- | --- | --- |
| 核心框架 | React + TypeScript | 组件化页面及交互逻辑 |
| 构建工具 | Vite | 开发服务器、生产构建和环境变量管理 |
| 路由 | TanStack Router | 类型安全路由、权限路由和页面参数 |
| 服务端状态 | TanStack Query | 请求、缓存、失效刷新、重试和分页 |
| 数据表格 | TanStack Table | 排序、筛选、列配置、选择和固定列 |
| 虚拟滚动 | TanStack Virtual | 大量 SKU 行及搜索结果渲染 |
| UI 基础组件 | Radix UI | 无障碍弹层、菜单、对话框等行为基础 |
| 样式系统 | Tailwind CSS + CSS Variables | 设计令牌、主题与页面布局 |
| 表单 | React Hook Form + Zod | 表单状态、前端校验及类型约束 |
| 本地状态 | Zustand | 命令面板、选择项和临时 UI 状态 |
| 图表 | ECharts | 库存、采购、销售和周转分析 |

前端设计要求：

- 不使用 Ant Design 等重视觉组件库作为页面基础，避免限制当前定制化界面；
- 服务端数据统一由 TanStack Query 管理，不复制到 Zustand；
- 表格必须支持服务端排序、筛选和分页，大数据量时启用虚拟滚动；
- 搜索中枢、SKU 表格、SKU 详情、适配信息、库存分布等拆成独立业务组件；
- 颜色、字号、间距、阴影和层级统一使用 CSS Variables，不在页面内散落常量。

### 3.2 后端

| 类别 | 选型 | 主要职责 |
| --- | --- | --- |
| 运行时 | 当前 Active LTS Node.js | 服务运行基础 |
| 应用框架 | NestJS | 模块边界、依赖注入、校验、权限和测试 |
| HTTP 引擎 | Fastify | REST 请求处理 |
| API 契约 | OpenAPI 3.1 | 文档、前端客户端和契约测试 |
| 数据校验 | Zod 或 Nest DTO | 请求边界校验；项目内统一一种写法 |
| ORM | Drizzle ORM | 类型安全 Schema、迁移和 SQL 查询 |
| 后台任务 | BullMQ | 导入、导出、同步、重试和任务进度 |

后端首期采用模块化单体，不采用微服务。所有业务模块运行在一个 API 应用中，但禁止跨模块直接读写内部数据；后台长任务由独立 Worker 进程执行。业务量或团队边界明确后，再按模块拆分服务。

### 3.3 数据与基础设施

| 类别 | 选型 | 说明 |
| --- | --- | --- |
| 主数据库 | PostgreSQL 18 | 关系数据、事务、索引、全文检索和审计数据 |
| 缓存与队列 | Redis | 缓存、分布式锁、频率控制和 BullMQ |
| 文件存储 | S3 兼容对象存储 | 商品图片、附件、导入源文件和导出文件 |
| 本地环境 | Docker Compose | PostgreSQL、Redis 和对象存储 |
| 生产部署 | 容器化部署 | Web、API、Worker 分别发布和扩容 |

## 6. API 设计约定

首期使用 REST，不使用 GraphQL。REST 更适合当前明确的资源、筛选、批量操作、外部系统对接及审计需求。

示例接口：

```text
GET    /api/v1/skus
POST   /api/v1/skus
GET    /api/v1/skus/:id
PATCH  /api/v1/skus/:id
GET    /api/v1/skus/:id/fitments
GET    /api/v1/skus/:id/inventory
GET    /api/v1/search/suggestions
POST   /api/v1/imports
GET    /api/v1/jobs/:id
```

统一规则：

- URL 从 `/api/v1` 开始；
- 列表接口默认服务端分页、排序和筛选；
- 普通后台列表可使用页码分页，大规模滚动或变更频繁的数据使用游标分页；
- 写接口支持幂等键，批量导入必须可以安全重试；
- 错误响应包含稳定错误码、用户可读信息和追踪 ID；
- OpenAPI 是前后端接口的唯一事实来源；
- 前端请求客户端从 OpenAPI 自动生成，不手写重复接口类型；
- 长任务返回任务 ID，前端通过轮询或 SSE 获取进度；只有强实时协作场景才引入 WebSocket。

## 7. SKU、OE、VIN 与 EPC 数据规则

### 7.1 SKU 主数据

- SKU 编码必须唯一，不承担可变业务含义；
- OE 号以独立关系表维护，一个 SKU 可以对应多个 OE 号；
- 保存 OE 原始值和标准化值，标准化用于搜索与去重；
- 品牌、分类、仓库、状态等使用字典或主数据表，不在页面中硬编码；
- 适配关系需要记录车型、年款、发动机、车身形式和适用条件；
- 库存数量由库存流水汇总，不允许直接无记录地覆盖结果。

### 7.2 EPC 数据

- 保存来源系统、抓取批次、来源时间和原始标识；
- EPC 原始名称、原始位置、原始条件及来源参考价格保持只读；
- 人工中文名称、销售价格和运营备注使用独立字段；
- 来源参考价格不得直接作为销售价格；
- EPC 发布为 SKU 时必须保留来源关系，便于追溯和重新同步。

### 7.3 审计

以下操作必须记录操作人、时间、变更前后值、来源和追踪 ID：

- SKU 创建、合并、停用和关键字段修改；
- OE 号、适配关系、采购价和销售价变更；
- 库存调整、调拨和锁定；
- EPC 数据发布、覆盖和解除关联；
- 批量导入和批量修改。

## 8. 搜索方案

首期使用 PostgreSQL，不提前引入 Elasticsearch/OpenSearch：

- SKU 编码和标准化 OE 号使用 B-tree 索引；
- 名称、车型和非精确 OE 查询使用 `pg_trgm`；
- 需要关键词组合时使用 PostgreSQL 全文检索；
- VIN 查询先解析车辆信息，再把车型条件用于适配查询；
- 搜索日志记录输入、结果数、耗时和最终点击项，用于发现无结果查询。

满足以下任一条件后再评估独立搜索引擎：

- PostgreSQL 索引优化后仍无法达到响应目标；
- 需要复杂相关性排序、同义词、拼音和跨域聚合；
- 搜索流量需要与交易数据库独立扩容；
- 数据规模和更新频率使数据库搜索明显影响交易负载。

## 9. 后台任务

下列任务由 Worker 处理：

- EPC 全量或增量同步；
- SKU、库存、采购价批量导入；
- Excel/CSV 批量导出；
- 图片压缩、格式转换和元数据提取；
- 搜索索引或统计汇总刷新。

任务必须具备：

- 明确状态：等待、执行中、成功、失败、取消；
- 可查询进度和错误明细；
- 幂等、超时、退避重试及失败告警；
- 原始导入文件和处理结果可追溯；
- 对库存、价格等关键写入使用事务和唯一约束防止重复。

## 10. 身份、安全与权限

- 生产环境使用 OIDC/OAuth 2.0 接入统一身份服务；
- 浏览器会话优先使用 Secure、HttpOnly、SameSite Cookie；
- 权限采用 RBAC，并为仓库、价格等敏感数据预留数据范围约束；
- 开发免登录只能在本地开发环境启用，生产构建必须强制关闭；
- 接口执行输入校验、权限校验、速率限制和敏感字段过滤；
- 密钥只通过部署环境的 Secret 管理，不写入仓库；
- 所有关键操作进入审计日志，审计记录不可由普通业务用户修改。

## 11. 测试与质量门禁

### 前端

- Vitest：工具函数、状态机和业务规则；
- Testing Library：组件交互与可访问性；
- Playwright：搜索、筛选、SKU 详情和批量操作等关键流程；
- 至少覆盖桌面 16:9、窄桌面和移动端降级布局。

### 后端

- 单元测试：领域规则和权限规则；
- PostgreSQL 集成测试：事务、约束、查询和迁移；
- OpenAPI 契约测试：响应结构和兼容性；
- 端到端测试：SKU 创建、EPC 发布、库存变更和批量导入。

合并前必须通过：格式化、Lint、TypeScript 类型检查、单元测试、构建和数据库迁移校验。

## 12. 可观测性与运维

- 所有请求生成追踪 ID，并贯穿 API、Worker 和审计记录；
- 日志使用结构化 JSON，禁止输出密码、令牌和完整敏感字段；
- 采集请求耗时、错误率、慢查询、队列积压和任务失败率；
- 接入 OpenTelemetry，错误聚合可以使用 Sentry 或同类服务；
- PostgreSQL 采用自动备份并定期验证恢复流程；
- Web、API、Worker 分开健康检查和发布，Worker 可以独立扩容。

## 13. 性能基线

首期开发按以下目标验收：

- 常用 SKU 列表接口 P95 小于 500 ms；
- 搜索建议接口 P95 小于 300 ms；
- 页面首屏加载后，筛选和行选择交互保持流畅；
- 前端不一次性加载全部 SKU；
- 导入、导出和 EPC 同步不占用普通 API 工作线程；
- 数据库查询必须有分页，上线前检查主要 SQL 的执行计划。

上述目标是工程基线，正式 SLA 应在真实数据量和部署规格明确后调整。

## 14. 实施顺序

1. 建立 Monorepo、统一配置和 CI；
2. 建立 Web、API、Worker 三个应用骨架；
3. 建立 PostgreSQL、Redis、对象存储和本地开发环境；
4. 定义 OpenAPI 规范、错误模型和生成客户端；
5. 建立用户、权限、字典、审计等平台基础；
6. 实现 SKU、OE、适配和 EPC 来源数据模型；
7. 实现 SKU 搜索、列表和详情页面；
8. 实现导入、导出及后台任务；
9. 接入库存、采购和销售模块；
10. 完成端到端测试、性能验证和生产部署。

## 15. 暂不采用的方案

- **Next.js**：本项目是内部 ERP，首期不需要 SEO 和服务端页面渲染；Vite SPA 更直接。
- **微服务**：首期增加部署、事务、排障和数据一致性成本，暂不采用。
- **GraphQL**：当前资源及集成边界明确，REST + OpenAPI 更容易治理和审计。
- **Elasticsearch/OpenSearch**：PostgreSQL 可以覆盖首期搜索需求，达到触发条件后再引入。
- **重型成品 UI 主题**：会限制既有视觉稿的还原，采用无样式或轻样式基础组件。
